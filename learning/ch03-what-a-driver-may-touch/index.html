Learning Tock from the ground up · Chapter 3

What a Driver May Touch

Chapter 2 left the kernel running and holding the whole chip. Every address, every peripheral, nothing standing in the way. Then you add a driver. This chapter is about how much of that the driver gets, and the answer turns out to be one field.

What you'll be able to do at the end

  • Name the one thing that decides everything a driver can reach.
  • Explain why a bug in a driver cannot corrupt the kernel, and point at the line that makes that true.
  • Follow a call from the LED driver down to the store from chapter 1, and say which layer first knows what chip this is.

Plan on forty minutes. Chapters 1 and 2 are assumed: what an address is, what a store does, and how the kernel got started.

Six words, before we start

Each is one sentence now and repeated in context below. None is hard.

capsule
Tock's word for a driver. An ordinary Rust struct with no special powers.
board
The crate that says which chip and which drivers one particular product has, and wires them to each other.
trait
A list of things a type promises it can do. The compiler checks the promise.
HIL
Hardware interface layer: a trait naming what a piece of hardware can do, without naming a chip.
generic
Code written against a trait instead of against one type, so a single copy serves every chip.
unsafe
The keyword marking Rust the compiler cannot check. Everything without it, it can.

The kernel has everything. A driver should not.

Chapter 2 ended with Tock running and holding the entire machine: every address, every peripheral, and nothing in the way — which is exactly where chapter 1 left off.

That is defensible for the kernel. It is thirty-two thousand lines, and every one of them is read by people who work on Tock itself.

Drivers are a different proposition. There are eighty-eight thousand lines of them, they are written one board at a time, and they are what a newcomer writes first. So the question chapter 2 ended on: when you add a driver, what should it be allowed to touch?

The usual answer is a rule and a code review. Here is what you may do; please do not do the other thing. Tock's answer is different, and it is the subject of this chapter. A driver reaches less than the kernel not because it agreed to, but because there is no way to write down the thing it would reach.

What a capsule cannot say

At the top of the crate that driver lives in there is a single line: #![forbid(unsafe_code)].

Rust has four settings for a rule like this, and they are not equally strong.

allow
say nothing
warn
say something, and build anyway
deny
an error — but code further down can turn it back off
forbid
an error, and turning it off is an error too

Capsule crates use the last one. So a capsule containing the word unsafe is not something a reviewer catches. It does not build.

So where is the unsafe?

Somewhere, something has to turn a number from the datasheet into a thing a program can use. Rust cannot check that step, because nothing in the language knows what is at 0xD0000000. The question is only how much code that step is allowed to contaminate.

The chain, end to end

A process asks for its first LED to be turned on. How that request crosses from the process into the kernel is chapter 6; pick it up on the kernel's side, in the capsule, and follow it down.

Twelve lines hold every address

Below the chip layer there is one more floor, and it is the last one. Each peripheral on the RP2350 gets a single declaration that turns its base address into a typed reference, and that declaration is where unsafe appears.

The function those twelve lines call is StaticRef::new, and it is declared unsafe because it cannot check its own argument. What it asks of the caller instead is written above it, in two lines:

ptr
must be aligned, non-null, and dereferencable as T
*ptr
must be valid for the program duration

Twelve callers make that promise once each, and what backs it is the datasheet. Everything above them — the chip layer, the HIL, the capsule — works in types and never has to make it again.

Who decides what a capsule gets

A capsule cannot ask for anything. It is handed what it has, in the board's main(), and it has that for the rest of the run.

One capsule, any chip

Figure 1 said the driver knows only that its type implements a trait. That is what generic means in practice, and it is what makes the next comparison possible: there is no second copy of this driver for the second board.

What this does not buy

Tock's own documentation calls a capsule semi-trusted, and the second half of that word is doing work.

taken away
it cannot reach memory it was never handed, so no bug in a capsule can corrupt the kernel or another capsule's state
left alone
it is compiled into the same binary and runs in the same address space, so it can still panic, and it can still refuse to return

Either one ends the machine. There is a single #[panic_handler] in the whole binary and its return type is !, meaning it never returns. The comment above that decision says why: the system "is no longer in a well-defined state".

On this board it then takes GPIO 25 for itself and blinks it forever — the same pin Figure 6 handed to the driver, driven now by the handler instead.

A loop is no better. A timeslice governs a process, not kernel code, so a capsule that never returns is never left.

Memory safety, then, and not good behaviour. That is the whole of what a type system was ever going to give, and it is why chapter 4 is about code the kernel does not compile at all.

Check yourself

A capsule holds one field: &'a [&'a L; NUM_LEDS]. Could it read back the value of gpio_out_set?

No. Nothing in scope is an address, and getting one would need unsafe, which the crate forbids. Chapter 1 adds a second reason: that register is write-only, so even the chip layer is promised nothing by reading it.

Which of the six steps in Figure 4 first knows the chip is an RP2350?

Step 5. Steps 3 and 4 are in the kernel's HIL and are shared by every chip; step 5 is the first line in a file that exists only for this one.

A capsule hits a loop it never leaves. What stops it?

Nothing. A timeslice governs a process; a capsule is called by the kernel and runs until it returns. This is the half of "semi-trusted" that the type system does not cover.

A board author hands the same pin to two capsules. What stops it?

Nothing. Both capsules hold a shared reference, which is legal Rust, and both would drive the pin. Figure 6's commented-out line is a person preventing it, and this is the weaker of the chapter's two guarantees.

What you can say now

A driver in Tock is a struct whose fields are the whole of its reach, in a crate where the word that would let it reach further does not compile. The address it eventually moves is named twelve floors down, once, by a line that quotes the datasheet.

That answers the question for code that ships inside the kernel binary and is trusted only that far. It says nothing about code that is not trusted at all.
