Learning Tock from the ground up · Chapter 1

Everything Is Memory

On a microcontroller, a peripheral is not a device you talk to. It is a set of memory addresses that do something when you read or write them. Once that clicks, most of embedded programming stops being mysterious — and the reason an operating system like Tock has to exist at all becomes obvious.

Verified against Tock at commit 47287a64e and the RP2350 datasheet (build 2025-07-29), targeting the Raspberry Pi Pico 2. Every address, register description and code excerpt below is quoted from one of those two documents, not from memory.

One line, all the way down

If you have used an Arduino, you have written something like digitalWrite(25, HIGH). It reads like a command issued to a device: pin, turn on.

It isn't. On this chip, the thing that actually changes the pin is a single store of a single 32-bit value to a single memory address. There is no message, no protocol, no driver conversation with a device. One write.

Layers around that store still do work — Arduino's helper checks and reconfigures things, and Tock's checks that you configured the pin as an output. But none of that is how the pin turns on. The store is.

The three highlighted instructions are the whole chapter.

lsl.w r1, r2, r1 is 1 << pin — a shift instruction, exactly what the Rust source says. and r1, r1, #0x1f masks the pin number down to five bits first. That is the compiler, not the chip: five bits count from 0 to 31, which is every shift position a 32-bit value has, so the mask makes the shift well-defined no matter what number it is handed.

And str r1, [r0, #0x18] is the store — but look at its shape. The address is not one number. It is a base held in a register, plus an offset baked into the instruction. r0 holds 0xD0000000; 0x18 is the offset of gpio_out_set within the block. That is why register blocks are written as a struct of offsets from a base address: the processor's addressing modes are built for exactly that shape, so it costs nothing.

The one thing above that is not the store: get_mode and the bls after it are the match guard from the Rust source, skipping the write if the pin was never configured as an output.

What an address actually is

A 32-bit processor can name 4,294,967,296 distinct byte-sized locations — that is what "32-bit" means here. Think of it as a numbered strip four billion slots long, from 0x00000000 to 0xFFFFFFFF.

On a desktop, nearly every slot you can reach is RAM, and the operating system decides what you may see. On a microcontroller there is no such indirection. The strip is wired directly to physical things, and different stretches of it are wired to different silicon. Some stretches are flash. Some are RAM. And some are not storage at all — they are the control panels of hardware blocks.

What happens when you read one back?

It is tempting to summarize all this as "registers aren't storage, they're doorbells." That is half right, and the wrong half matters.

Some registers really do behave like storage. GPIO_OUT at 0xD0000010 is one. The datasheet's description of it reads "Set output level (1/0 → high/low) for GPIO0…31. Reading back gives the last value written, NOT the input value from the pins." Write to it, read it, and you get your value back. The datasheet types it RW.

GPIO_OUT_SET, eight bytes further along, does not. Its entire description is an operation applied to a different register — word for word, "Perform an atomic bit-set on GPIO_OUT, i.e. GPIO_OUT |= wdata". Its two neighbors are spelled out the same way: GPIO_OUT_CLR is GPIO_OUT &= ~wdata, and GPIO_OUT_XOR is GPIO_OUT ^= wdata.

So the value you write here is not kept anywhere. It is consumed as an argument. Write a value with no bits set and nothing happens at all — no storage location in the world silently discards a write like that.

One detail worth noticing, because it is the kind of thing that bites later: the datasheet types GPIO_OUT_SET as WO, write-only. Tock's chip crate declares it ReadWrite<u32>, which is looser than the hardware contract. Nothing breaks today, because the kernel only ever writes it — but the type permits a read the hardware never promised to answer.

So the real lesson is sharper than "doorbell": what an address does on a read, and on a write, is a decision the hardware designer made for that one register. The address itself tells you nothing about it. You cannot infer the behavior; you can only look it up.

Where 1 << 25 comes from

One register controls a whole bank of pins at once, because a 32-bit register has thirty-two independent bits. Bit 0 is GPIO 0, bit 25 is GPIO 25. To act on pin n you set bit n, and the idiom for "a value with only bit n set" is 1 << n. That is the whole reason the Tock source reads 1 << self.pin.

Be careful with an assumption that looks safe here: a 32-bit register does not imply thirty-two pins. Tock's RP2350 crate defines pins GPIO0 through GPIO29 — thirty of them, not thirty-two. Bits 30 and 31 are real bits in a real register with no pin behind them on this chip. Register width and pin count are two separate facts, and only one of them is visible in the code.

Careful — your board is the W

Pin 25 is the onboard LED on a plain Pico 2, and that is what boards/raspberry_pi_pico_2/src/main.rs:385 assumes. On the wireless variants, GPIO 25 is wired to the CYW43439 radio's SPI chip-select instead. Raspberry Pi's own board header for this exact board says so outright:

#define CYW43_DEFAULT_PIN_WL_REG_ON   23u
#define CYW43_DEFAULT_PIN_WL_DATA_OUT 24u
#define CYW43_DEFAULT_PIN_WL_CLOCK    29u
#define CYW43_DEFAULT_PIN_WL_CS       25u
#define CYW43_WL_GPIO_LED_PIN          0

pico-sdk, src/boards/include/boards/pico2_w.h

So on your Pico 2 W this write will not light anything — it will toggle the radio's chip-select. The LED is CYW43_WL_GPIO_LED_PIN 0: a pin on the wireless chip, which the RP2350 can only reach by talking to that chip over SPI first.

Worth sitting with, because it is the first real lesson about layering: the chip says "pin 25." What pin 25 is connected to is a fact about the board. Confusing the two is how you spend an afternoon debugging an LED that was never there.

Why the same pins have four registers

Look closely at the SIO register block and something looks redundant. Four different registers all control the same bank of output pins:

(0x010 => gpio_out)        // GPIO0..31 output value
(0x018 => gpio_out_set)    // GPIO0..31 output value set
(0x020 => gpio_out_clr)    // GPIO0..31 output value clear
(0x028 => gpio_out_xor)    // GPIO0..31 output value XOR
chips/rp2350/src/gpio.rs, lines 89–105

If gpio_out already holds the output state, then turning on pin 25 is obviously gpio_out |= 1 << 25. So why did the designers spend silicon on three more registers that do things you could already do?

Because |= is not one operation. It is three: read the current value, OR in your bit, write the result back. Any change somebody else makes in the gap between your read and your write — an interrupt handler, or the other CPU core running at that instant — is erased when your write lands, because your write carries the value you read before they touched it. The RP2350 has two cores, so this is not hypothetical.

The chip designers were thinking about two cores here. The datasheet's description of GPIO_OUT says exactly what happens when both hit it at once:

If core 0 and core 1 both write to GPIO_OUT simultaneously (or to a SET/CLR/XOR alias), the result is as though the write from core 0 took place first, and the write from core 1 was then applied to that intermediate result.

Read that carefully, because it is a promise about stores, and it does not rescue you. Two simultaneous writes are cleanly serialized, one after the other, with a defined outcome. But |= is not a write. It is a read, then a write, with a window in between — and the damage is done by the stale value your read returned, long before the store this paragraph is talking about ever happens.

Step through it and watch a write disappear.

Why volatile has to exist

There is one more thing standing between your Rust and the silicon: the optimizer.

A compiler reasons about memory the way you would reason about variables. If you write a value to an address and never read it, the write is dead code — delete it. If you write twice, only the last one matters — delete the first. If you read the same address in a loop and nothing modified it, hoist the read out. Every one of those transformations is correct for ordinary memory and catastrophically wrong for a doorbell, where the write itself is the point and where the value can change without any code touching it.

volatile is how you tell the compiler this address is one of those. Every access happens, exactly as many times as written, in the order written, and none may be invented, removed, or reordered relative to each other.

In Tock this is not something you remember to do — it is baked into the register types, so it is impossible to forget:

// impl<T, R> Writeable for ReadWrite<T, R>
fn set(&self, value: T) {
    unsafe { ::core::ptr::write_volatile(self.value.get(), value) }
}
tock-registers 0.10.0, src/registers.rs:63 — the bottom of every write to a ReadWrite register. Three near-identical siblings cover the WriteOnly, Aliased and InMemoryRegister types at lines 119, 164 and 208.

What the unsafe is doing there

If you have worked through the Rust Book but not yet reached its Advanced Features chapter, this is the first thing to know: unsafe here is not an admission that the code is dangerous. It is a claim — "I have checked the thing the compiler cannot check." Dereferencing a raw pointer could be catastrophic if the address were wrong, and Rust has no way to verify that 0xD0000018 is a real register. So a human asserts it, in a block small enough to audit.

That pattern — a tiny audited unsafe core wrapped in a safe API that no one can misuse — is the single most characteristic move in the whole Tock kernel. You will see it constantly. Here, it means every pin.set() in the codebase is a safe call in Rust's sense of the word, and the trust for all of them is concentrated in four three-line functions that a reviewer can read in a minute.

So here is the problem

Take stock of what is now true. Peripherals are memory addresses. Writing to them has physical effects. And on a bare microcontroller, any code running on the chip can write to any address at any time.

There is no permission to check. No kernel to ask. The store instruction to 0xD0000018 is exactly as permitted as a store to a variable of your own, and costs about as much. A stray pointer in some unrelated sensor routine can drive a lock relay, reconfigure a UART mid-transmission, or scribble over the flash controller's registers.

That is not a bug in anyone's code. It is the default condition of the machine.

Every single thing Tock does is an answer to that one sentence — any code can write any address. Its capsules, its processes, its grants, the MPU configuration it programs before letting your application run: all of it exists to put something between arbitrary code and arbitrary addresses. Chapter by chapter, that is the story we are going to build.

Chapter 2 — How code starts running

Before anything can write to a register, something has to be executing. We will follow the RP2350 from the instant power arrives to the first line of Tock's main() — the reset vector, what the boot ROM is looking for in that 1 KB reserved in front of the kernel, and what "initialize RAM" actually means when RAM contains garbage.

Things worth carrying forward from this chapter:

  1. A peripheral is an address, not a device.
  2. What an address does on read and write is a per-register design decision. Look it up; never infer it.
  3. One register, one bit per pin, hence 1 << n — but register width is not pin count.
  4. Read–modify–write is three operations and can be torn apart.
  5. volatile stops the optimizer from helpfully destroying your driver.
  6. Nothing yet stops any code from touching any address.
