Learning Tock from the ground up · Chapter 1

Everything Is Memory

On a microcontroller, a peripheral is not a device you talk to. It is a set of memory addresses that do something when you write to them. Once that clicks, most of embedded programming stops being mysterious — and the reason an operating system like Tock has to exist at all becomes obvious.

Written against Tock at commit 20adc62c2, targeting the RP2350 (Raspberry Pi Pico 2). Every address and code excerpt below is quoted from the repository, not from memory.

One line, all the way down

If you have used an Arduino, you have written something like digitalWrite(25, HIGH). It reads like a command issued to a device: pin, turn on.

It isn't. Underneath every layer, that operation is a single store of a single 32-bit value to a single memory address. Nothing more happens. There is no message, no protocol, no driver conversation. One write.

Here is the entire ladder on the RP2350, from the friendliest layer to the instruction the processor actually executes.

What an address actually is

A 32-bit processor can name 4,294,967,296 distinct byte-sized locations — that is what "32-bit" means here. Think of it as a numbered strip four billion slots long, from 0x00000000 to 0xFFFFFFFF.

On a desktop, nearly every slot you can reach is RAM, and the operating system decides what you may see. On a microcontroller there is no such indirection. The strip is wired directly to physical things, and different stretches of it are wired to different silicon. Some stretches are flash. Some are RAM. And some are not storage at all — they are the control panels of hardware blocks.

Storage, or a doorbell?

This is the reframe the whole chapter turns on, so it is worth being blunt about it.

When you write to RAM at 0x20000100, a value is kept. Read the address back and you get what you put there. The address behaves like a box.

When you write to 0xD0000018, nothing is kept. The write causes a physical voltage to appear on a pin and is then gone. Read that address back and you do not get your value returned — that address isn't even readable as what you wrote. The address behaves like a doorbell: pressing it has an effect, but the button does not remember being pressed.

Where 1 << 25 comes from

One register controls thirty-two pins at once, because a 32-bit register has thirty-two bits and the chip has thirty-two GPIO pins in that bank. Bit 0 is GPIO 0, bit 25 is GPIO 25. To act on pin n you set bit n, and the idiom for "a value with only bit n set" is 1 << n.

That is the whole reason the Tock source reads 1 << self.pin. Drag the slider and watch the value assemble itself.

Careful — your board is the W

Pin 25 is the onboard LED on a plain Pico 2, and that is what boards/raspberry_pi_pico_2/src/main.rs:385 assumes. On the wireless variants, GPIO 25 is wired to the CYW43439 radio's SPI chip-select instead — you can see exactly that in Tock's Pico W board file at boards/raspberry_pi_pico_w/src/main.rs:126. So on your Pico 2 W, this write will not light anything; it will wiggle the radio's chip-select line.

Worth sitting with, because it is the first real lesson about layering: the chip says "pin 25." What pin 25 is connected to is a fact about the board. Confusing the two is how you spend an afternoon debugging an LED that was never there.

Why the same pins have four registers

Look closely at the SIO register block and something looks redundant. Four different registers all control the same thirty-two output pins:

(0x010 => gpio_out)        // GPIO0..31 output value
(0x018 => gpio_out_set)    // GPIO0..31 output value set
(0x020 => gpio_out_clr)    // GPIO0..31 output value clear
(0x028 => gpio_out_xor)    // GPIO0..31 output value XOR
chips/rp2350/src/gpio.rs, lines 89–105

If gpio_out already holds the output state, then turning on pin 25 is obviously gpio_out |= 1 << 25. So why did the designers spend silicon on three more registers that do things you could already do?

Because |= is not one operation. It is three: read the current value, OR in your bit, write the result back. Anything that happens between the read and the write — an interrupt firing, or the other CPU core running at the same instant — can be clobbered by that final write. The RP2350 has two cores. This is not hypothetical.

Step through it and watch a write disappear.

Why volatile has to exist

There is one more thing standing between your Rust and the silicon: the optimizer.

A compiler reasons about memory the way you would reason about variables. If you write a value to an address and never read it, the write is dead code — delete it. If you write twice, only the last one matters — delete the first. If you read the same address in a loop and nothing modified it, hoist the read out. Every one of those transformations is correct for ordinary memory and catastrophically wrong for a doorbell, where the write itself is the point and where the value can change without any code touching it.

volatile is how you tell the compiler this address is one of those. Every access happens, exactly as many times as written, in the order written, and none may be invented, removed, or reordered relative to each other.

In Tock this is not something you remember to do — it is baked into the register types, so it is impossible to forget:

pub fn set(&self, value: T) {
    unsafe { ::core::ptr::write_volatile(self.value.get(), value) }
}
tock-registers 0.10.0, src/registers.rs:63 — the bottom of every register write in the kernel

What the unsafe is doing there

Since you have the Rust Book but not its Advanced Features chapter yet: unsafe here is not an admission that the code is dangerous. It is a claim — "I have checked the thing the compiler cannot check." Dereferencing a raw pointer could be catastrophic if the address were wrong, and Rust has no way to verify that 0xD0000018 is a real register. So a human asserts it, in a block small enough to audit.

That pattern — a tiny audited unsafe core wrapped in a safe API that no one can misuse — is the single most characteristic move in the whole Tock kernel. You will see it constantly. Here, it means every pin.set() in the codebase is a completely safe call, and the trust is concentrated in one three-line function.

So here is the problem

Take stock of what is now true. Peripherals are memory addresses. Writing to them has physical effects. And on a bare microcontroller, any code running on the chip can write to any address at any time.

There is no permission to check. No kernel to ask. The store instruction to 0xD0000018 is exactly as fast and exactly as allowed as a store to your own local variable. A stray pointer in some unrelated sensor routine can drive a lock relay, reconfigure a UART mid-transmission, or scribble over the flash controller's registers.

That is not a bug in anyone's code. It is the default condition of the machine.

Every single thing Tock does is an answer to that sentence. Its capsules, its processes, its grants, the MPU configuration it programs before running your application — all of it exists to put something between arbitrary code and arbitrary addresses. Chapter by chapter, that is the story we are going to build.

Chapter 2 — How code starts running

Before anything can write to a register, something has to be executing. We will follow the RP2350 from the instant power arrives to the first line of Tock's main() — the reset vector, why 0x10000000 has a 1024-byte bootloader carved out in front of the kernel, and what "initialize RAM" actually means when RAM contains garbage.

Things worth carrying forward from this chapter:

  1. A peripheral is an address, not a device.
  2. A write can be a doorbell rather than a box.
  3. One register, thirty-two pins, hence 1 << n.
  4. Read–modify–write is three operations and can be torn apart.
  5. volatile stops the optimizer from helpfully destroying your driver.
  6. Nothing yet stops any code from touching any address.
