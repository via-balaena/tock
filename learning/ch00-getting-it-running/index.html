Getting It Running

The rest of this series reads Tock's source and checks every claim against the tree it lives in. This chapter is the twenty minutes before that: putting Tock on a chip you can hold, and getting it to say one sentence back to you.

What you'll be able to do at the end

  • Build Tock for this board, and say where the file it produces ends up.
  • Put that file on the chip with one command, and say what the command is talking to.
  • Wire three signals, and read the one line that means the kernel is up.
  • Name which of the four flashing routes in this board's Makefile will do nothing on a Mac, and why it does nothing quietly.
  • Tell a dead board apart from a wrongly wired console, which produce the same silence.

Plan on forty minutes, and most of it is wiring. Nothing in this chapter is assumed from the rest of the series, because there is no chapter before it. You need the hardware in the first figure and a machine you can install Rust on.

Thirteen words, before we start

Each is one sentence now and used in context below. None is hard, and several are ordinary words being used narrowly.

board
The small circuit board with the chip on it. Also, in this repository, the code that says which chip and which parts one product has.
kernel
The program that starts first and stays in charge of the machine. Tock is one.
flash
Memory that keeps what it holds when the power is off. Also the verb for writing it.
pin
One of the numbered contacts along the edge of the board. Each is a wire the chip can drive or read.
compiler
The program that turns the source you can read into the code a chip can run.
crate
A Rust package: one unit the compiler builds at a time.
toolchain
The compiler and the pieces around it, pinned here to one exact version so that everyone builds the same thing.
target
The machine being built for, written as a triple. It is never the machine doing the building.
ELF
The file a compiler emits: the program, plus a description of where each part of it belongs.
UF2
A different file shape, designed to survive being copied onto a drive. The chip's built-in loader accepts it.
probe
A small adapter that turns a USB port into wires which can halt another chip and write its flash.
console
The serial line the kernel prints to, and the prompt it offers you at the other end of it.
baud
Bits per second on a serial line. Both ends have to agree, or what arrives is unreadable.

Why this chapter exists

Everything after this reads source. That works from an armchair, and for five of the seven chapters that follow you never have to touch anything.

But the last chapter closes by telling you to stop reading and run a command, and until now the series never said how to get to the point where that command works. This chapter is that gap, filled in.

It is also worth doing for its own sake. A claim about a kernel you have watched boot is a different kind of claim from one you have only read about, and the difference shows up the first time something does not work.

One command builds it

Tock pins its toolchain in a file at the top of the tree, so there is no version to choose and nothing to decide. At the commit this chapter is written against, rust-toolchain.toml asks for the nightly of 21 July 2026, and lists the targets it wants installed alongside it.

Rust reads that file on its own. The first build in a fresh clone spends a while fetching that toolchain, and after that:

$ cd boards/raspberry_pi_pico_2
$ make
    Finished `release` profile [optimized + debuginfo] target(s) in 5.64s
   text    data     bss     dec     hex filename
  69164       0   19020   88184   15878 raspberry_pi_pico_2

That is the whole build, and the number is real: seven seconds of wall time on an Apple laptop, of which five and a half are the compiler. A kernel is a small program, and this is one of the quiet pleasures of the work.

The three numbers are worth a glance even now. Around 69 kB of code, no initialised data, and 19 kB of space the kernel wants at runtime for variables that start out empty.

Four ways to flash, and two of them are quiet about failing

This board's Makefile offers four routes onto the chip. They are not four flavours of one thing: two drive the probe, two produce a UF2 and copy it to a drive that the board pretends to be when you hold its button down.

The split that matters is not which is more modern. It is that the two copying routes check for a folder, and when that folder is not there they print a suggestion and exit successfully. On a Mac that folder is never there.

Getting it onto the chip

With the probe wired to the three pads, one command does it:

$ make flash-openocd

OpenOCD is the one piece of software you install for this, and on the Mac these pages were written on it was the only thing missing. Everything else was already there for Rust.

What that runs is OpenOCD, an ordinary program on your machine that speaks to the probe over USB, and through it to the chip. The board's own configuration for it is two lines long: use a standard debug adapter, and the chip is an RP2350.

The command writes the kernel, reads it back to confirm it landed, resets the board and exits. If it cannot find the probe it says so and stops, which is the failure you want — loud, immediate, and about the thing that is actually wrong.

Making it talk

The board is now running Tock and telling you nothing, because nothing is listening. The kernel prints to a serial line on two pins, and the probe has a second connector for exactly this.

Which pins is not a convention to look up, it is a line in this board's own source: pin 0 transmits and pin 1 receives, at 115200 baud. Those two pins are handed to the console and are not available for anything else.

The line that means it worked

Open the probe's serial port at 115200 and reset the board. What you are waiting for is one line, and the kernel prints it at the end of its own setup, immediately before it starts running anything else:

Initialization complete. Enter main loop
tock$

That is the whole success signal. The first line comes from a single call near the bottom of this board's start-up code, and its only job is to be the thing you are reading now. The second is a prompt, and it means a great deal more than it looks like.

One machine, or two

Everything above assumed one machine doing both jobs, so that the computer which compiled the kernel is the one with the probe in it. That is the simplest arrangement and nothing is wrong with it.

It is not the only one. The two jobs have almost nothing to do with each other, and you may not want unfamiliar hardware plugged into the machine your work lives on.

What makes splitting them cheap is how little has to cross. The far machine needs no copy of this repository and no Rust at all. It needs OpenOCD, and a way to receive one file.

Tock's own hardware testing is built this way, which is worth knowing as confirmation rather than as coincidence. Its workflow describes a testbed of small hosts sitting next to real boards, while the building happens on ordinary machines elsewhere.

Written out, the split is two commands rather than one:

# on the machine that builds
$ scp target/thumbv8m.main-none-eabi/release/raspberry_pi_pico_2.elf \
      appliance:

# on the machine with the probe
$ K=raspberry_pi_pico_2.elf
$ openocd -f interface/cmsis-dap.cfg -f target/rp2350.cfg \
      -c "adapter speed 5000" \
      -c "program $K; verify_image $K; reset; shutdown;"

Those two -f arguments are not invented here. They are the two lines of this board's own OpenOCD config, spelled out, which is exactly why the far machine can get by without a copy of the repository. The rest of the line is what the Makefile target runs.

When nothing happens

The hard part of this chapter is not any single step. It is that several different failures produce the same nothing, and without a way to separate them you end up changing two things at once and learning nothing from either.

If the board on your desk is a Pico 2 W

This is worth reading before you buy anything, because the wireless version of this board is the easier one to find and it is not the board this series is written against.

The repository has crates for four Pico boards, and none of them is a Pico 2 W. The crate with a _w in its name is built on the earlier chip, so it is not a substitute.

The concrete cost is one pin. On a plain Pico 2 the user light is on pin 25, and that is the pin this board's directory hands to the light driver. On a Pico 2 W the same pin belongs to the radio, and the light is somewhere the kernel cannot reach at all.

So everything in this chapter up to the light still applies: it builds, it flashes, it boots, and it talks. What you do not get is the blink, which is the one signal that needs no console.

Whether that kernel runs correctly on a Pico 2 W beyond that has not been tested here, and this page will not pretend otherwise. The chips are the same family and the extra parts simply go unclaimed, so it is plausible. Plausible is not the standard the rest of these pages hold themselves to.

Check yourself

make flash prints a message about a variable and exits without an error. What happened?

It built. The copy is the only step that did not happen, and it did not happen because the folder it checks for is a Linux path that a Mac never has. The exit status is success, so nothing after it notices, and the board goes on running whatever it held before.

The banner appears on the console, but typing list does nothing at all. What is wrong?

One wire. The banner arriving proves the board's transmit and the shared ground are both good, and proves the kernel is up. The only thing left untested is the other direction, which is the probe's transmit to the board's receive.

Why does the output path contain thumbv8m.main-none-eabi rather than something naming your computer?

It names the target: the chip's instruction set, no operating system beneath it, and a standard calling convention. Two different laptops building this produce the same path, because the path is about the destination rather than the origin.

You see nothing on the console and no error from anything. What is the first thing to change?

The cable. Charge-only USB cables are common, and a board powered through one comes up and blinks and cannot be reached, which looks exactly like a fault worth debugging for an hour. It costs ten seconds to rule out, so it goes first.

What you can say now

You have a board running a kernel you built, and a line of text proving it. That is the ground everything after this stands on: when a later chapter says the kernel does something, you have somewhere to go and watch it happen.

You also have the beginnings of a habit this series cares about more than any particular fact. Two of the four ways to flash this board fail without saying so, and the way you find that out is by checking what a command did rather than what it reported.
